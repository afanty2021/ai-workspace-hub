# Research Closeout（研究收口）

> 把一次研究分流成可复用知识、可验证假设和后续跟踪任务，而不是把整篇报告复制到各处。

## 收口步骤

1. 更新同一份 `output/research/` 报告，纳入讨论中被修改或推翻的判断；确认报告有稳定研究 ID，以及 `preflight_id / knowledge_used / wiki_pages_loaded` 和对应扫描回执。若曾人工降级扫描，写清失败原因和人工检查范围。**深度研究报告（deep_research_template）确认含「技术面验证」段，缺失退回补全**（Q-20261109-03）。若本次研究应用「深度研究四模块」，收口时在 `workspace/research-profile.md`「本轮观察」补一行观察（含「第 N 次应用」序号），**写入前核对既有最大序号连续——跳号=有研究漏记账**（第 17/19 次曾两度漏记，2026-11-11 max 评审 r2 修根）。**收尾两查（2026-11-12 尾批 max 评审修根，硬规则第 2 次触发）**：①序号断言——`grep -o '四模块第 [0-9]* 次' workspace/research-profile.md | tail -1` 的输出序号必须等于新行序号 −1（跳号=漏记、撞号=重复，首日双案：8a6dd39 跳号误报+R20261112-18 撞号 37）；②入库状态——向用户陈述任何文件「已入库/已提交」前必跑 `git check-ignore <路径>`，`.gitignore` 命中即不得称入库（output/*、wiki/entities/* 均在忽略清单，profile 观察行才是唯一入库沉淀）。**批量 / 无人值守批次加第三查（Q-20261114-04 修根 B）**：跑 `python3 system/scripts/workspace_status.py` 核对「四模块序号账本」行=OK 才算收口完成（报告声明序号↔profile 观察行全局对账，preflight 回执引用已豁免；异常明细=漏记/撞号/profile 撞行）。
2. 给出结论状态：`暂不成立 / 暂定成立 / 证据较强 / 待关键数据`，并说明决定状态的证据。**「观察等待 / 待关键数据」类裁决必须附时间变量触发器**（流动性/产业价格/公司事件，EXP-20261109-01 质检线——只给空间结论不给触发器 = 半份裁决，退回补全）。**「Alpha 兑现条件」一问（2026-11-14 补入，Q-20261114-09②，Attention Beta 评文落地）**：结论状态前必答——本裁决若最终成立，赚钱靠什么兑现：①公司盈利/E 兑现（真 Alpha，锚在财报与产业读数）；②主题 β 延续/注意力溢价（Theme Beta，锚在资金与叙事）。两者必须分开写，混写=没答；Theme Beta 主导的裁决须注明「兑现代价=主题退潮时与 β 同跌」，并联动主题暴露矩阵（`workspace/monitoring/theme-exposure-matrix.md`）标注该票所属暴露组与同 β 票清单。
3. 按内容分流，写入 wiki 前仍需用户确认：
   - 单一外部来源摘要 -> `wiki/sources/`
   - 公司长期事实档案 -> `wiki/entities/`
   - 可复用概念或框架 -> `wiki/concepts/`
   - 跨来源阶段性判断 -> `wiki/explorations/`
   - 新建或更新 exploration 时补齐生命周期字段，并运行 `knowledge_lifecycle.py rebuild-index --apply` 重建三类短索引。
   - 新建 wiki 页面后，调用 `system/scripts/wiki_tagger.py tag ... --apply` 补齐统一结构化标签；API 失败写入收口回执，不编造或静默跳过。
   - **跨文件数字对拍（同日批次产出 ≥2 份文件时必做，2026-11-12 max 评审修根）**：同一关键比例/金额会在报告、卡、entity、profile 间转引，收口前 grep 对拍两件事——①一致性：同一事实同一数字，无法本地裁决的双口径必须两处显式标注并挂待验证回源；②来源存在性：事实表每个精确数字须能在 `based_on` 报告中找到，找不到的删掉、改写回源口径、或降入推测节。首案：EXP-20261112-01 两条无源数字进事实表+枫叶互动参股 49.24/49.16 双口径（friction-log 2026-11-12，数字转引错误第 4 类「跨文件漂移」）。**观察哨/触发器日期同查（2026-11-12 当日评审 I-1 增补）**：报告里的前瞻日期（财报日/FOMC/披露窗）转引到 config watchlist 观察哨、`workspace/monitoring/` 看板、`hypothesis/` 观察哨节时，收口前按日期串（如 `11-17`、`11-19`）grep 全仓对拍，勘误日期必须同步改完全部 live 锚，dated check log 保留原记不改史；首案：NVDA 财报日 11-19→11-17 勘误只改了 profile/active-context，config 两行+dashboard+H1 五处 live 锚漏改，且 profile「H1 观察哨同步」陈述与 H1 文件实际不符。
4. 筛选投资假设。只有同时满足“影响决策、可验证/证伪、有时间范围”才进入 `hypothesis/`。默认把共同驱动抽象为自上而下的主题假设，公司作为受益映射；不要把同一产业逻辑复制成多个公司假设。
5. 每条假设必须包含：核心逻辑、当前确定性、时间范围、支持与反方证据、跟踪指标、催化剂、证伪条件、关联标的、来源研究报告。
6. 将关联标的加入股票池前先征得用户确认；日报只跟踪已确认对象。
7. 所有尚未当场执行的确认项写入 `workspace/review-queue.md`：wiki 沉淀、假设建立/调整、股票池新增、研究偏好固化。确认后执行并把状态改为 `done`。
8. 更新 `workspace/meta/active-context.md`，写清下一次复盘触发条件。
9. 若本次产生可迁移结构，只记为待复盘的 exploration；不在单次研究中直接晋级成 rule。后续按 `system/skills/knowledge-lifecycle.md` 做跨案例验证、归因、升降级和调用复盘。

## 统一回执

结束时告诉用户：本次研究结论、更新了哪些知识、建立了哪些假设、开始跟踪哪些指标、哪些事项仍待验证，以及下一句可直接使用的指令。

假设使用 `Hn`，研究使用 `RYYYYMMDD-NN`；关联写入双方 frontmatter。当前状态只改 frontmatter，正文状态日志只追加历史。
